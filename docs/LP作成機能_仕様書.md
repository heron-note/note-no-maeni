# LP作成機能 仕様書

> **対象プロジェクト**: noteのまえに（heron-note.github.io）への追加機能  
> **作成日**: 2026-09-14  
> **ステータス**: 設計確定・実装前

---

## 1. 概要

### 1-1. 何を作るか

「noteのまえに」アプリに、ユーザー自身の GitHub Pages サイトを作成・管理・公開できる機能を追加する。

### 1-2. どんなサイトが作れるか

note 記事・商品・自己紹介などを組み合わせた、**モジュール式のパーソナルサイト**。  
ポートフォリオ専用にも、おすすめ記事紹介サイトにも、アーカイブ検索サイトにもなる。  
サイトの目的・対象読者はユーザーが自由に決める。アプリ側は関与しない。

### 1-3. ターゲットユーザー

- **ITリテラシー**: 低〜中（GitHub アカウントを持っていない人も対象）
- **共通点**: noteのまえにのユーザーであること
- **前提**: 複数サービスへの登録・設定は無理。GitHub だけで完結させる

## 2. システム全体構成

```
【開発者（へろん）が管理】
  noteのまえに アプリ
    heron-note.github.io/note-no-maeni/
    └─ LP作成・管理UIを追加する

  JS / テンプレート（CDN）
    heron-note.github.io/lp-template/
    └─ main.js, template files
    └─ 開発者が更新 → 全ユーザーのLPに即時反映

  認証中継サーバー（Cloudflare Workers・無料枠、3章参照）
    └─ GitHub Device Flow のCORS回避用プロキシ。秘密情報は持たない

【ユーザーの GitHub】
  LP公開用リポジトリ（公開・アプリが自動作成、GitHub連携の解放後にLP作成を選んだ場合のみ作成）
    user/note-lp/
    ├─ index.html        ← テンプレート本体（滅多に変わらない）
    ├─ data/
    │   ├─ config.json   ← ブロック構成・テーマ・プロフィール設定
    │   ├─ articles.json ← note記事一覧
    │   └─ products.json ← 商品一覧
    ├─ images/           ← アップロード画像
    └─ .github/workflows/
        └─ fetch-ogp.yml ← note記事OGP自動取得ワークフロー

  汎用データリポジトリ（非公開・GitHub連携の初回にアプリが自動作成）
    user/note-no-maeni-data/
    ├─ license.json      ← 有料機能の解放マーカー（3-1参照）
    └─ （将来）休もっ化テンプレート・設定など、他機能のデータもここに追加していける

【公開サイト】
  GitHub Pages で自動公開
    user.github.io/note-lp/
    ├─ index.html が読む: JS → heron-note.github.io/lp-template/main.js
    └─ index.html が読む: データ → 同リポジトリの data/*.json
```

### 更新の2層構造

| 操作 | 方法 | 頻度 | 破壊リスク |
|------|------|------|-----------|
| 記事・商品の追加 | JSON のみ更新（GitHub API） | 毎日複数回 | ゼロ |
| デザイン・ブロック設定変更 | config.json 更新（GitHub API） | 週数回 | ゼロ |
| index.html 再デプロイ | アプリがボタン表示→ユーザーが押す | 機能追加時のみ | 管理下 |
| JS 更新 | 開発者が lp-template を更新 | 開発者判断 | 即時全反映 |

## 3. 認証

### 方式: GitHub OAuth Device Flow（2026-09-14 決定・PAT方式から変更）

対象ユーザーはITリテラシー低〜中・スマホオンリーが多いため（1-3参照）、「Personal Access Token を自分で発行してコピペする」PAT方式は離脱要因になると判断し、**Device Flow**（SSOに近い操作感の認証方式）に変更する。

Device Flow はユーザー側の操作が「短いコードをタップ・入力して承認するだけ」で済み、トークンという概念に触れさせずに済む。

#### 必要になった中継サーバー（Cloudflare Workers）

GitHub は Device Flow のエンドポイントへのブラウザからの直接アクセスを CORS でブロックしているため、静的サイトだけでは完結できない。ごく小さな中継サーバーを1つ追加する。

- **役割**: ブラウザからのリクエストを GitHub の Device Flow エンドポイントへそのまま転送するだけ（CORS回避のためだけの薄いプロキシ）
- **保持する秘密情報**: なし。Device Flow は `client_id` のみで完結し `client_secret` は不要なため、このサーバーは何も機密情報を持たない
- **想定コスト**: Cloudflare Workers 無料枠（1日10万リクエストまで無料）で十分。個人開発規模のアクセス量では実質ゼロコスト運用が可能
- これが本アプリで初めて持つサーバーコンポーネントになる

### 必要な権限スコープ

- `repo`（リポジトリの作成・読み書き）
- `workflow`（GitHub Actions の起動）

### 初期セットアップフロー

```
1. ユーザーが「GitHub連携」ボタンを押す
2. アプリ（→中継サーバー経由）が GitHub にデバイスコードを要求
3. 画面に短いユーザーコード（例: ABCD-1234）と github.com/login/device へのリンクを表示
4. ユーザーがリンクをタップ → GitHubにログイン済みならワンタップで承認（未登録ならその場でアカウント作成）
5. アプリ（→中継サーバー経由）が承認完了をポーリングで検知し、アクセストークンを取得
6. アプリがトークンを使ってリポジトリを自動作成（テンプレートから）
7. GitHub Pages を有効化
8. 完了 → 以降はアプリ内だけで操作
```

### アクセストークンの保管（2026-09-15 更新）

- **localStorageに永続化する**（`nob_`プレフィックスとは別枠のキーに保存し、バックアップのエクスポート対象・GitHub同期対象からは除外する）
- 毎回のDevice Flow再承認は手間が大きいと判断し、一度連携したら次回起動時も自動的に連携済み状態から始められるようにする
- ただし起動時に必ず「データリポジトリの有効チェック」（10章）を行う。トークン失効・リポジトリ誤削除等で無効と判定された場合は、連携状態だけを解除する（ローカルデータには触れない）

## 3-1. 提供モデル・価格（2026-09-15 更新）

### 価格体系: データお引っ越しは無料、LP作成のみ買い切り（サブスクリプションではない）

| 機能 | 内容 | 価格 |
|------|------|------|
| データお引っ越し | アプリデータ（休もっ化テンプレート・設定等）をGitHubで管理し、端末間の引っ越し・複数端末同時利用を可能にする | **無料** |
| LP作成 | 本仕様書のメイン機能 | 買い切り（金額は別途決定） |

データお引っ越しを無料にする理由: GitHub連携自体のハードルを下げて多くの人に使ってもらうための入り口と位置づける。GitHub連携さえ済ませてもらえれば、その先でLP機能（Home画面の「LP管理」ボタン、11-1参照）に自然に触れてもらえる導線になり、無料機能がそのままLP機能の販促を兼ねる。開発側のコストも元々ゼロ（ユーザー自身のGitHubで完結するため）なので、無料化によるデメリットは実質ない。

LP作成の具体的な金額は未定（別途決定）。理由: リポジトリ・GitHub Pages・GitHub Actions はすべてユーザー自身の GitHub アカウント上で完結し、当社側に継続的なサーバーコストが発生しないため、都度課金ではなく売り切り型にできる。

### 決済方式: note 有料記事での販売（2026-09-14 決定）

本機能は「note のまえに」という note 専用ツールであり、購入者は必ず note アカウントを持っている。決済インフラを自前で持たず、**note 自体で販売する**。有料なのはLP作成のみのため、note有料記事もLP作成用の1本でよい。

```
1. 開発者が note に「LP作成」の有料記事を投稿する
   - 内容: 機能の説明 + 購入後に表示される「解放コード」
2. ユーザーが記事を購入する（決済は note が処理。返金対応も note のルールに従う）
3. ユーザーは記事に書かれた解放コードをアプリの設定画面にコピペする
4. アプリがコードを検証し、LP作成機能を解放する
```

- note には購入確認 API が無い（6章参照）ため、アプリ側でサーバーレスに検証できる方式が必要。

### 解放コードの検証方式: 公開鍵署名（2026-09-14 決定）

**課題**: 解放状態は非公開データリポジトリ内の `license.json` に保存する方式（後述）だが、このリポジトリはユーザー自身の GitHub アカウントなので、ユーザーは `license.json` を直接編集する権限を持つ。単純に「正解のコードのハッシュ値」をアプリに埋め込んで比較する方式では、その期待ハッシュ値自体がアプリのJSコードから丸見えになり、ユーザーは本物のコードを知らなくても期待ハッシュ値をそのまま `license.json` に書き込むだけで解放判定を通せてしまう。ハッシュ比較は「うっかり改ざん」を防ぐ程度で、本質的な防御にならない。

**解決策**: ハッシュ比較ではなく、公開鍵暗号の**デジタル署名**で検証する。

- 開発者だけが持つ秘密鍵で、機能ごとに決めた固定メッセージ（例: `"note-no-maeni-datasync-v1"` / `"note-no-maeni-lp-v1"`）に対して署名を1つ作成する
- その署名（Base64文字列）を「解放コード」として、対応する note 有料記事に掲載する
- アプリ側には**公開鍵**のみを埋め込む（見られても偽造の役には立たない）
- ユーザーがコードを入力すると、アプリはその署名文字列をそのまま `license.json` に保存する
- 以降、アプリは起動のたびに「この署名は公開鍵で検証できる本物か」をその場でチェックする（ブラウザ標準の Web Crypto API で完結、追加ライブラリ不要）
- ユーザーが `license.json` を直接書き換えても、秘密鍵を持たない限り検証を通る正しい署名を作れないため、でたらめな値では解放されない
- 残る限界: 同じ署名（コード）が第三者に流出・転載された場合、他人もそのコードで解放できてしまう。これはサーバーを持たない前提での構造的な限界として許容する（対処しない）

### license.json の構造（2026-09-15 更新: データお引っ越しは無料化に伴い署名不要）

データお引っ越しは無料機能になったため、署名検証の対象は `lp` のみ。`license.json`自体は「GitHub連携済みかどうか」を示すためファイル存在は維持するが、`dataSync`キーは持たない（GitHub連携が成立していれば無条件で無料機能は使える）。

```json
{
  "lp": { "signature": "MEQCIB..." }
}
```

### 解放状態の保存方法（2026-09-14 決定）

解放済みかどうかを判定するために「LP用リポジトリ（`note-lp`）の有無」を使う案は不採用とした。
理由: GitHub を汎用のファイル置き場として今後ほかの（無料の）機能にも応用する可能性があり、その場合に無料機能が作ったリポジトリを誤って「課金済み」と判定してしまう危険があるため。

代わりに、**解放専用のマーカーファイル**で判定する。

- GitHub連携の初回接続時、アプリは非公開の汎用データリポジトリ `user/note-no-maeni-data` を確認・作成する（2章の構成図参照）
- 各機能が解放済みかどうかは、そのリポジトリ内の `license.json` 内の対応する署名の検証結果のみで判定する（`note-lp` リポジトリの有無やその他ファイルの状態には一切依存しない）
- この汎用データリポジトリは、将来的に他機能（休もっ化テンプレートの同期など）が独自のファイルを追加する共有の置き場としても使える。ただし解放判定には常に `license.json` の署名検証だけを使う、というルールを崩さない

### GitHub連携〜機能解放のフロー（2026-09-15 更新）

「コード入力 → GitHub連携」という2段階の壁は作らず、GitHub連携フローの中で必要な人にだけコード入力を挟む。

```
1. ユーザーが「GitHub連携」を開始（Device Flow）
2. アプリが user/note-no-maeni-data リポジトリを確認（無ければ作成）
   → この時点でデータお引っ越し（無料）はすぐ使える
3. LP機能を使おうとした場合のみ、license.json を確認
   - lp の署名があり検証も通る → そのまま機能解放（コード入力不要。再インストール・機種変更時はこれだけで済む）
   - 署名が無い、または検証に失敗する → その場で解放コード入力欄を表示
4. 入力されたコード（署名）が公開鍵で検証できたら、license.json に書き込み、LP機能を解放する
```

## 4. ブロック一覧

ユーザーが ON/OFF・並び順・表示形式を自由に設定できるモジュール単位。

| ブロックID | 名称 | 説明 |
|-----------|------|------|
| `profile` | プロフィール | 名前・アイコン・自己紹介文 |
| `featured` | おすすめ記事 | 厳選した note 記事をトップに大きく表示 |
| `collection` | 特集コレクション | テーマ別にまとめたシリーズ紹介 |
| `portfolio` | ポートフォリオ | 作品をギャラリー形式で表示 |
| `articles` | 記事一覧 | 全記事をグリッド表示・ページング |
| `categories` | カテゴリ絞り込み | タブでカテゴリ切り替え（記事一覧と連動） |
| `search` | アーカイブ検索 | キーワード・タグで記事を検索 |
| `products` | 商品紹介 | Kindle・Booth 等の商品一覧 |
| `image` | 画像ブロック | 任意位置に画像を埋め込む |
| `links` | SNSリンク | note・各 SNS へのアイコンボタン（Font Awesome使用、軽量な円形アイコン） |

### ブロックの共通仕様

- **ON/OFF**: 個別に有効・無効を切り替え可能
- **並び順**: ドラッグ＆ドロップで自由に入れ替え
- **表示形式**: ブロックごとに複数の選択肢から選ぶ（後述）
- **画像ブロック**: 複数配置可。ブロックリストの任意位置に挿入

### 表示形式の選択肢（例）

| ブロック | 選択できる表示形式 |
|---------|-----------------|
| 記事一覧 | カード型 / リスト型 / マガジン型 |
| おすすめ記事 | 大バナー型 / グリッド型 / スライド型 |
| 商品紹介 | カード型 / コンパクトリスト型 |
| ポートフォリオ | 正方形グリッド / 横長バナー / マソンリー |
| プロフィール | センター型 / 横並び型 |

> 表示形式の詳細は実装フェーズで確定する

### 4-1. ヘッダー（テーマ設定・2026-09-14 決定）

サイト最上部の「画像＋サイト名」は、並び替え可能なブロックではなく **`theme.header`（テーマ設定）** として扱う。
理由: ヘッダーは常にページ最上部に固定される要素であり、ブロックリストに混ぜると「並び替えできてしまう」誤解を生むため。

- ユーザーはヘッダー画像（ロゴ／バナー）を自由にアップロードして配置できる
- ロゴ位置は `left`（左寄せ＋横並び）/ `center`（中央揃え）から選択
- サイト名テキストは `meta.siteTitle` を表示に流用する（項目を二重管理しない）
- サイト名のフォントは `theme.fontFamily` で選択したフォントが適用される（4-2参照）
- 画像・サイト名のどちらも未設定なら、ヘッダー自体を描画しない

### 4-2. サイト名フォントの選択（2026-09-14 決定）

`theme.fontFamily` に、Google Fonts から厳選した日本語フォントのプリセットキーを保存する。
アプリ側は各フォントのサンプル文字を並べた **グラフィカルな選択UI**（実際のフォントで見た目を確認できるカード一覧）を提供する。

lp-template 側はキー名から Google Fonts の `<link>` を動的に挿入し、サイト名・見出し（プロフィール名、各ブロックタイトル）に適用する。本文には適用しない（可読性優先）。

プリセット例: `default`（標準）/ `rounded`（丸ゴシック）/ `mincho`（明朝）/ `pop`（ポップ）/ `hand`（手書き風）/ `stylish`（スタイリッシュ）

### 4-3. ナビゲーションメニューについて（2026-09-14 決定）

LP は複数ページを移動する構成ではなく、1ページ完結のスクロール型サイトのため、**サイト全体を横断する従来型メニューは設けない**。
有効ブロックへジャンプする簡易アンカーナビ（スティッキーな小タブ）は将来検討事項とし、Phase 1 では実装しない（13章参照）。

### 4-4. 対応SNS一覧（2026-09-14 決定）

`links` ブロックで対応する SNS（`config.json` の `links` オブジェクトのキー）:

| キー | サービス | アイコン (Font Awesome) |
|------|---------|------------------------|
| `note` | note | `fa-regular fa-note-sticky`（note固有ロゴはFont Awesome非対応のため代替） |
| `x` | X (旧Twitter) | `fa-brands fa-x-twitter` |
| `instagram` | Instagram | `fa-brands fa-instagram` |
| `facebook` | Facebook | `fa-brands fa-facebook` |
| `tiktok` | TikTok | `fa-brands fa-tiktok` |
| `line` | LINE | `fa-brands fa-line` |
| `youtube` | YouTube | `fa-brands fa-youtube` |
| `threads` | Threads | `fa-brands fa-threads` |

未設定のキーはボタンを表示しない。将来追加したいSNSがあれば `lp-template/main.js` の `SNS_LABELS` / `SNS_ICON_CLASSES` にキーを追加するだけで対応可能。

### 4-5. テーマカラーのプリセット（2026-09-14 決定）

`theme.primaryColor` はプリセットからの選択に加え、自由なカラーピッカーでのカスタマイズも可能とする（値は任意の16進カラーコード、lp-template側はバリデーションなしでそのまま適用）。

アプリ側が提示するプリセット例:

| プリセット名 | カラーコード |
|-------------|-------------|
| ブルー（標準） | `#4A90D9` |
| グリーン | `#6FA96F` |
| ピンク | `#E08FA0` |
| オレンジ | `#E8A33D` |
| パープル | `#9B7FD4` |
| モノトーン | `#6B6B6B` |

## 6. note 記事 URL 追加フロー

note には API がないため、GitHub Actions を OGP プロキシとして使う。

```
1. ユーザーがアプリに note 記事 URL を貼り付ける
2. アプリが GitHub API でワークフローを起動
   POST /repos/{owner}/{repo}/actions/workflows/fetch-ogp.yml/dispatches
   body: { ref: "main", inputs: { url: "https://note.com/..." } }
3. GitHub Actions が起動（サーバーサイドで CORS 問題なし）
   - note ページの HTML を取得
   - OGP タグ・ハッシュタグ・投稿日をパース
   - articles.json に追記してコミット
4. 約20秒後、アプリが完了を検知して通知
5. LP に自動反映
```

### OGP から取得できる情報（実測済み）

| 項目 | 取得元 |
|------|--------|
| タイトル | `og:title` |
| 説明文 | `og:description` |
| サムネイル | `og:image`（assets.st-note.com） |
| 記事URL | `og:url` |
| ハッシュタグ | ページ本文パース |
| 投稿日時 | ページ本文パース |

### ハッシュタグの割り当て（2026-09-14 決定）

- ページから取得した `#〜` のハッシュタグは `articles.json` の `tags`（配列）にすべて格納する
- `category`（分類・カテゴリタブ用の単一値）には、取得したハッシュタグの**先頭の1件を初期値として自動セット**する
  - ただしこれは下書き扱いで、ユーザーがアプリ上でいつでも変更・空欄化できる
  - 記事ごとにバラバラな単語がカテゴリとして乱立しないよう、既存カテゴリからの選択もアプリ側で提示する
- 取得元は note が一般公開しているページの HTML（ログイン不要で誰でも閲覧できる情報）であり、OGP取得と同様 GitHub Actions が通常のページ取得と同じ扱いで行う。ただし note の利用規約（自動取得・クローリングに関する条項）は運用開始前に最新版を確認すること

## 10. アプリ内キャッシュ方針

### LPデータ（`note-lp`リポジトリ）

- アプリ側に永続データは持たない（GitHub リポジトリが唯一のデータソース）
- 起動時に GitHub API から `config.json` / `articles.json` / `products.json` を取得
- セッション中はメモリキャッシュ。再起動時は再取得
- GitHub側（`note-lp`）が削除・消失した場合、ローカルにバックアップは無いため復元できない（記事の貼り直し等で復旧）。LP機能はGitHub Pagesでの公開が前提の機能であり、GitHubありきの設計として許容する（3-1参照）

### アプリ全般データ（`note-no-maeni-data`リポジトリ、2026-09-15 決定）

休もっ化テンプレート・設定・画像など、元々ローカル（localStorage/IndexedDB）に保存されている既存データをGitHubにも同期する場合の方式。LPデータとは異なり、**ローカルキャッシュが常に存在する**ことを前提にした設計にする。

#### 起動時の整合性チェック

```
GitHub連携済みの場合、起動時に:
1. 接続・リポジトリ（note-no-maeni-data）自体が有効か確認
   - 無効（リポジトリごと消えている、トークン失効等） → アプリの「連携済み」状態だけを解除する。
     ローカルの設定・画像は一切削除しない（誤ってGitHub側が消えても、ローカルの手元データは守られる）
   - 有効 → 2へ
2. GitHub側のインデックスファイル（後述）とローカルの保有状況を突き合わせ、リソース単位で確認
   - インデックスにあるがGitHub側の実体が個別に削除されている → ローカルの対応するキャッシュも削除して同期する
   - GitHub側に存在する → ローカルへ反映（他端末での更新を取り込む）
```

「接続そのものの生死」と「個別リソースの生死」を別レイヤーで扱う。前者が無効なら何も壊さず安全側に倒し、前者が有効な場合に限り、後者の削除をローカルにも反映する。

#### 更新の流れ（ローカルファースト）

```
1. ユーザーが設定・画像等を変更
2. まず localStorage / IndexedDB に書き込む（即座に反映、オフラインでも動作）
3. その後バックグラウンドで GitHub（note-no-maeni-data）へアップロード・更新する
```

#### 画像データの容量対策

画像はローカルストレージを圧迫しやすいため、既存の件数制限（例: `EyecatchCreator.tsx`の`HISTORY_MAX`等）はそのまま維持し、上限を超えた分は**ローカルには保存せず、GitHubへ直接アップロードのみ**行う。

- 上限内: ローカル＋GitHub両方に保持（高速アクセス・オフライン動作）
- 上限超過分: GitHubのみに保持（実質無制限だが、ローカルからは都度取得が必要）

#### インデックスファイル

`note-no-maeni-data`リポジトリ内に、リソース一覧を管理するインデックスファイル（例: `index.json`）を持たせる。ローカル保持分・GitHubのみ保持分の両方を含む一覧とし、GitHub側のファイルツリーを都度APIで列挙しなくても全体像が分かるようにする。具体的なスキーマは実装時に設計する（13章）。

#### 設定画面のバックアップダウンロードへの影響（2026-09-15 決定）

既存のSettings画面「バックアップ」機能（[Settings.tsx](../src/screens/Settings.tsx)、[transfer.ts](../src/utils/transfer.ts)）は、現状ローカル（IndexedDB/localStorage）のみを読んでJSON1ファイル（画像はBase64埋め込み）としてダウンロードする。GitHub連携時はローカル上限を超えた画像がGitHub側にしか無いため、この方式のままだとバックアップが不完全になる。連携有無で出力形式を切り替える。

- **未連携、または連携済みでもローカル上限内**: 従来通りJSON1ファイル（変更なし）。画像がBase64埋め込みなのはローカルの保存形式（IndexedDBのdataURL）をそのまま使っているためで、この場合は許容する
- **連携済みでGitHubのみの画像がある場合**: GitHubから該当画像をバイナリのまま取得し、**ZIP**（画像ファイル本体＋メタデータJSON）としてダウンロードする。`package.json`に既存の`jszip`依存を利用でき、新規ライブラリ追加は不要
- ボタンの見た目・操作感は変えず、内部処理のみ連携状況で自動的に切り替える
- ZIPダウンロード機能自体は、将来的にバックアップ以外の用途（画像一括ダウンロード等）にも転用できる

## 11. 既存アプリ「noteのまえに」との関係

### 11-1. アプリ内導線（2026-09-14 決定）

「LP管理」と「GitHub連携（お引っ越し）」は使用頻度・性質が異なるため、置き場所を分ける。

| 機能 | 置き場所 | 理由 |
|------|---------|------|
| GitHub連携（お引っ越し） | Settings画面（[Settings.tsx](../src/screens/Settings.tsx)の「バックアップ」行付近に新設） | 連携さえ済めば自動で効く機能で、日常的に操作する画面ではない。相棒クリエイト等と同じ「設定して終わり」系の置き場でよい |
| LP管理 | Home画面の右吹き出しパネル（[Home.tsx:193-203](../src/screens/Home.tsx#L193-L203)、アイキャッチ作成・記事ストッカーの下に3つ目の`speech-bubble-right`を追加） | 記事追加・並び替え・デプロイなど継続的にメンテナンスする運用画面のため、導線を短くする必要がある。アイキャッチ作成・記事ストッカーと同じ「コンテンツ運用系」のグループなので右パネルに合流させる |

- `bubble-panel-right`は`position: absolute; top: 50%; transform: translateY(-50%)`で独立して上下中央寄せされるため、右パネルが2個→3個になっても左パネルとの対称性には影響しない
- 未購入ユーザーにもLP管理アイコン自体は表示し、タップ時に購入案内（note有料記事への導線＋解放コード入力）を出す。アイコンの存在自体が発見経路・販促になる

**開発中の暫定対応（2026-09-15）**: LP作成機能はまだ実装・販売準備が整っていないため、「LP管理」ボタンは実装しつつも**当面は非表示**にする（フィーチャーフラグで出し分け）。データお引っ越し（GitHub連携）は無料機能として先行して表示・提供する。
